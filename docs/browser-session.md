# Browser session contract

The static UI uses `/api/v1/auth/browser/login`, `/session`, and `/logout`. Browser login returns only `userId` and `username`; it never returns the JWT in JSON. The login request accepts an optional `totpCode` (6–8 digits, sent only when the user typed one) for MFA-enrolled accounts; a missing or wrong code fails with the generic 401 like a bad password unless the account's MFA attempt budget is exhausted, which answers 429 before the code is evaluated. Public auth endpoints (`/auth/login`, `/auth/register`, `/auth/password/reset/*`) never require the session cookie: the JWT filter skips cookie authentication on them so a stale cookie on a shared browser cannot turn a public request into a 401 before authorization is evaluated. The server sets an `HttpOnly; SameSite=Strict; Path=/` session cookie and a separate, JavaScript-readable random CSRF cookie. The UI copies the latter into `X-CSRF-Token` for state-changing requests. Cookie-authenticated mutations with no matching header receive 403. The filter verifies JWT signature first (so the blacklist is never an oracle), then enforces revocation on every authenticated request — except the exact logout action, which re-admits a still-valid signed token so a lost logout response can be retried idempotently; the logout use case short-circuits an already-revoked token to a side-effect-free 204 (no re-blacklist, no audit row), closing the revocation oracle. The existing `/api/v1/auth/login` and `/logout` Bearer contract remains for API clients and does not use the browser CSRF header.

**Logout is public and works with an expired access token.** The logout endpoints authenticate with the credentials they PRESENT (the access token and/or the refresh token) and revoke exactly those — requiring a still-valid session would make logging out impossible once the access token had expired: the filter rejected the request with 401, the controller never ran, the session cookies were never cleared, and the server-side refresh session stayed alive for its full lifetime. A logout is a termination request, not an authorization decision, and it grants nothing. The CSRF binding cannot be checked on that path (the binding subject comes from the token that could not be verified), which is not a gap: the browser session cookie is `SameSite=Strict`, so a cross-site request carries no cookie and the controller has nothing to revoke.

**The refresh cookie is scoped to the browser-auth endpoints** (`Path=/api/v1/auth/browser`), not to the refresh endpoint alone. The logout endpoint needs the refresh token to revoke the server-side session; with the previous single-endpoint path the browser never presented it on logout, so a logout left the refresh session alive. It is still never sent to API calls, and it is `HttpOnly` + `SameSite=Strict`.

The `prod` profile sets `app.security.browser-session.secure=true`. This uses `Secure` cookies with `__Host-` names, which require HTTPS at the browser edge and cannot specify a Domain attribute. Local HTTP development uses unprefixed cookies. Do not set `secure=false` for a public deployment. Configure CORS origins explicitly; do not add a wildcard or an untrusted origin while credentials are enabled.

The UI discards any JWT left in `localStorage` by an earlier version. Session restoration after a reload uses the cookie and `GET /api/v1/auth/browser/session`; no JavaScript storage contains the session token. A failed logout request leaves the UI signed in so it cannot claim server revocation was confirmed. Retry logout or wait for token expiry. A successful logout revokes the JWT and expires both cookies. Operators should verify logout and session restoration through the deployed TLS ingress, including two replicas and a revocation-backend outage. The repository integration test covers the application contract, not that deployment path.

`HttpOnly` blocks JavaScript from reading the cookie but does not make same-origin XSS harmless: injected code can still issue actions as the signed-in user. Keep the restrictive CSP, validate/sanitize rendered content, and test the real browser UI before release. The anti-CSRF cookie/header check protects cookie-authenticated mutations against cross-site form requests; it is not an XSS defense.
